## 1. Functional spec

### 1.1 Overview

When a story author revokes a user's fanartist role on their story, that user
is notified (website, and Discord if they enabled that channel). Today the
revocation is silent: the user just finds they can no longer submit.

### 1.2 Vocabulary

| Term | Meaning |
|------|---------|
| Rôle de fanartiste | Per-story permission to submit fanart without a request |
| Révocation | Author removes that role from a user on a story |

### 1.3 Roles & visibility

| Role | Can see | Can do |
|------|---------|--------|
| Guest / `user` | nothing | nothing |
| `user-confirmed` ex-fanartist | the notification (name = revoking author, story link) | unchanged otherwise |
| Author / co-author | n/a | revoke (existing); now triggers the notification |
| Moderator / Admin | n/a | no revocation path exists |

### 1.4 Functional requirements

1. An author revokes a fanartist on the collaborators screen (existing action).
2. If a role row was actually deleted, the ex-fanartist receives `fanart.role_revoked`,
   sender = revoking author, payload like the other `fanart.*` types (story title/slug).
3. Text (fr): « Votre rôle de fanartiste sur <story> vous a été retiré ». Links to the story.
4. Revoking a user who is not a fanartist (double click, stale page): nothing deleted, nothing sent.
5. The revoked user's existing fanarts are untouched (existing behaviour).
6. Discord delivery follows the user's generic channel preference; no special case.
7. The revoker is never a recipient (author revoking themself: nothing).

### 1.5 Lifecycle

Notification is a snapshot (story title/slug, actor name/slug); survives story
deletion like the other fanart notifications. Recipient deleted: nothing sent
(existing `send()` swallows it). Recipient deactivated: same as other fanart
notifications. Role rows removed by user deletion or story deletion send nothing.

### 1.6 Cross-cutting concerns

| Concern | Decision |
|---------|----------|
| Roles | Only authors revoke (existing policy); recipient was a confirmed user |
| Visibility / privacy | Reveals only the story and the revoking author's public profile |
| Settings | New type appears in the notification preferences, group Fanarts, like the others |
| Notifications | New type `fanart.role_revoked`; Discord automatic |
| Domain events | N/A — no event consumers needed |
| Statistics | N/A |
| Moderation | N/A |
| Lifecycle / cascade | See 1.5 |
| Media | N/A |
| Search | N/A |
| i18n | French text and preference label |
| Mobile | N/A — plain notification text |
| Accessibility | N/A |

### 1.7 Out of scope

- Removing fanarts on revocation; blocking uploads differently.
- Notifications for fanart removal paths (already exist).
- Notifying when roles vanish through user or story deletion.
- Rewriting past notifications.

None.

## 2. Architecture

### 2.1 Domain placement

Fanart only. Mirrors `fanart.role_given` / `role_declined`.

### 2.2 Data model

None.

### 2.3 PHP architecture

- `FanartRoleRevokedNotification extends FanartNotificationContent` (`type()` = `fanart.role_revoked`, `langKey()` = `role_revoked`), registered in `FanartServiceProvider`'s type loop.
- `FanartNotifier::fanartRoleRevoked(int $storyId, int $revokedUserId, int $actorId)`: recipients `[$revokedUserId]`, content via `forStory`.
- `FanartistService::revoke(int $storyId, int $userId, int $actorId): void` notifies only when the delete count is > 0.
- `FanartistController::destroy` passes `Auth::id()`.

### 2.4 Frontend

None (lang strings only).
